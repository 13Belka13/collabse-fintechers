# Модель v2.5: банк исполняет условия сделки агентов, а не судит товар

Статус: черновик на проверку, 20.10.2026. Заменяет схему «банк проверяет содержимое поставки правилами и ИИ-судьёй» (SPEC §8).
v2.5 учитывает семь проверок критиком. Изменения против v2.4 — в приложении А, источники — в приложении Б.
Правило правок: механику берём у проверенных аналогов и пишем «как у X». Опоры делятся на **внедрённые** (работают на рынке: торговое финансирование ICC, Visa, Upwork, Escrow.com, AAA, UDRP) и **проектные** (черновики и прототипы: ADRP, AP2, ASP, x402r, Circle Refund Protocol). Своё помечаем «наше».
Числа — предложение команды, если не указан источник. [Р] — рассуждение, требует проверки юристом.

## 0. Принципы

1. **Банк работает с документами, а не с товаром** — как в торговом финансировании ICC: выдача против обеспеченной оплаты (инкассо, URC 522 ст. 7), проверка документов на соответствие условиям (аккредитив, UCP 600 ст. 14), частичные выплаты (UCP 600 ст. 31). Банк проверяет только объективное: время, подписи, количество и предикаты, которые человек покупателя подтвердил. Спор о качестве (правило C) решает **внешний решающий**; банк исполняет решение, дел не решает и качество не оценивает.
2. **У агента покупателя нет денежных ключей.** Он может только попросить банк оплатить согласованную сделку (`pay(deal_id)`); деньги уходят только на кошелёк проверенного продавца. Запросы агента подписываются неденежным ключом покупателя.
3. **Покупатель получает только то, за что платит.** Непрошедшие позиции к нему не попадают (§5.2).
4. **Спорные деньги не выплачиваются, пока спор не решён, и не возвращаются покупателю по умолчанию.** Они остаются в эскроу в сети весь срок спора: срок эскроу длинный (§8.3), а завершает сделку банк сам — выплатой и финальным возвратом.
5. **Где нужен человек** (и как часто):
   - человек покупателя: подписывает мандат с SCA (раз в несколько месяцев); подтверждает условия задачи (раз на задачу); подтверждает платежи выше порога мандата (редко); «принять всё равно» (по желанию);
   - внешний решающий: только спор C на У2 (доли процента сделок);
   - комплаенс банка: AML-случаи;
   - по запросу продавца-физлица: проверка результата автокодов человеком (GDPR ст. 22).
   Всё остальное — автоматически.
6. **Банк не несёт неограниченного риска.** Его расходы — собственные ошибки (по закону) и не больше одной суммы сделки при сбое; при массовом сбое новые авторизации приостанавливаются.

Ответ на кейс трека: «spending limits» — мандат (§2); «disputes and refunds between non-humans» — автокоды и правила качества (§6–§7); «dispute path a human can follow» — страница сделки (§11) и демо со спором C (§14).

Что модель **не обещает**: защиту от данных, которые формально соответствуют условиям, но неправдивы без доказательства, датированного до поставки. От этого — гарантия B (заложена в цену), спор C и открытая статистика продавца (§9).

**Чего блокчейн не даёт:** банк держит ключ плательщика и является оператором эскроу, поэтому может вернуть деньги покупателю в любой момент. Блокировка в сети — проверяемое доказательство для продавца, что деньги есть; она фиксирует получателя и потолок комиссии; каждое движение видят обе стороны. От самого банка продавца защищают лицензия и договор. Цепочка — общий проверяемый журнал для агентов двух компаний.

## 2. Мандат

Как сейчас: лимит на сделку, на месяц, бюджет задачи, порог подтверждения человеком, версии с хэшем.

**SCA:** мандат подписывается с SCA. Платежи агента внутри мандата — по исключению для защищённых корпоративных процессов (RTS 2018/389 ст. 17: только для юрлиц и при согласии надзора). Если ČNB не согласится — запасные основания: ст. 13 (человек с SCA один раз добавляет продавца в доверенные получатели) и ст. 16 для У0 (малые суммы: до 30 €, накопительно 100 € или 5 операций) [Р].

Новое:

```json
"unprotected_budget_eur_per_day": 20,
"session_budget_eur_per_day_per_seller": 50,
"dispute_floor": [
  {"tier_sum_eur": "<= 20",     "min_tier": "T0"},
  {"tier_sum_eur": "(20; 500]", "min_tier": "T1", "min_window_min": 30, "allowed_quality": ["A", "B"]},
  {"tier_sum_eur": "> 500",     "min_tier": "T2", "min_window_h": 72, "allowed_quality": ["A", "B", "C"]}
],
"require_b_for": ["data_purchase"],
"require_c_above_eur": 2000,
"claim_fee_budget_eur_per_month": 1000
```

- **`tier_sum`** = наибольшее из (сумма сделки; сумма сделок и сессий с этим продавцом за 24 ч, включая эту). Полуинтервалы: ≤ 20 / (20; 500] / > 500. Сумма по задаче влияет только на лимиты мандата.
- **`unprotected_budget_eur_per_day`** — общий лимит У0 по всем продавцам; плюс 20 € на одного продавца.
- **`session_budget_eur_per_day_per_seller`** — общий лимит сессий с одним продавцом за сутки; сессии входят в `tier_sum`.
- **`require_b_for`**, **`require_c_above_eur`** — где мандат требует гарантию B или спор C.
- **`claim_fee_budget_eur_per_month`** — бюджет сборов за спор C, отдельно от лимита на сделку.
- Бюджет резервируется при `pay` и остаётся зарезервированным до финального расчёта.

### 2.1 Условия задачи
Агент извлекает из задачи человека предикаты приёмки (§6). Человек подтверждает их один раз на задачу, видя их **человеческим языком и с 3 примерами прошедших и непрошедших позиций**; для частых задач — шаблоны в мандате. Хэш условий записывается в задачу. Предложение продавца обязано содержать подтверждённые предикаты **дословно** (может добавить свои, убрать — нет); иначе банк отказывает.

## 4. Уровни

| | **У0 «Мгновенный»** | **Сессия** | **У1 «Документарный»** | **У2 «С решающим»** |
|---|---|---|---|---|
| `tier_sum` | ≤ 20 € | Микроплатежи сверх У0, в пределах `session_budget` | (20; 500] € | > 500 € или по выбору продавца |
| Рельс | x402 exact через фасилитатор банка | Одна авторизация на сессию, capture по ваучерам | Эскроу, доставка через банк | Эскроу, доставка через банк |
| Окно претензий | Нет | Нет | 30 мин – 24 ч | 72 ч – 14 дней |
| Автокоды (§6) | Только ошибки банка | Только ошибки банка | Все | Все |
| Правила качества (§7) | — | — | A или B | A, B, C |
| Люди | Нет | Нет | Нет | Только решающий в C |
| Комиссия банка (предложение) | 0,2 %, списанием со счёта продавца раз в месяц | 0,2 % при capture | A: 0,8 %, B: 1,2 % | 1,5 % |

- **Сессия для микроплатежей:** одна авторизация на сессию. На каждый запрос агент покупателя подписывает неденежным ключом **кумулятивный ваучер** «оплачено N запросов, итого S» (как в платёжных каналах). Банк делает capture по последнему ваучеру, остаток — финальный void. Эскроу по использованию как идея — у Fortytwo x402Escrow (там сумму сообщает фасилитатор, ваучеров нет).
- **C при дроблении:** если сумма с продавцом за сутки > 500 €, C доступно для всех сделок этой группы.

## 5. Поставка через банк

Доставка и квитанция — **одно событие**: продавец передаёт набор банку, банк пересчитывает его и выдаёт покупателю **только принятые позиции**. Принцип выдачи против обеспеченной оплаты — из документарного инкассо (URC 522 ст. 7); отличие: в инкассо банк не проверяет содержание документов, а здесь проверяет их соответствие условиям, как в аккредитиве (UCP 600 ст. 14). Отсчёт сроков — только от сдачи через банк (как Submit Work у Upwork).

### 5.1 Формат
- Область: конечные наборы JSON-позиций, до 10 МБ на поставку. Потоковые данные — через сессию (§4).
- JSON — по I-JSON (RFC 7493): числа больше 2^53 — строками; строки в NFC; в `json_schema` без внешних `$ref`. Канонизация позиции — RFC 8785 (JCS).
- Лист: `H(0x00 ‖ uint64_be(index) ‖ JCS(item))`, узел: `H(0x01 ‖ left ‖ right)`, `H` = SHA-256; нечётный узел поднимается без дублирования. Банк публикует эталонную реализацию и тестовые векторы.
- **Манифест** (EIP-712, подпись ключом продавца): `{deal_id, offer_hash, version, count, merkle_root, nonce}`.
- Позиция может содержать `source_url` — тогда нейтральный сервис банка при приёме сохраняет датированный снимок источника (нужно для доказательств класса C, §7C.2).

### 5.2 Поток
1. Банк блокирует сумму в эскроу; продавец проверяет блокировку в сети (`verify_escrow`): получатель, `feeReceiver` = счёт банка, `minFeeBps ≤ maxFeeBps` = тариф, сроки, payer. PaymentInfo сделки имеет соль `keccak(deal_id ‖ n)`, поэтому продавец сам связывает её со сделкой.
2. Продавец отправляет банку набор + манифест.
3. Банк фиксирует **время приёма по своему журналу** (оно и есть время поставки) и проверяет: ключ продавца действует в момент приёма; `deal_id`, `offer_hash`, `nonce`; срок поставки; **сам пересчитывает корень и число позиций**. При несовпадении банк сразу возвращает свой корень, продавец может прислать ту же версию заново до срока.
4. **Банк** прогоняет автокоды §6 и считает **сумму к оплате P** (за принятые позиции).
5. **Выдача:** `fetch_delivery` отдаёт покупателю **только принятые позиции** текущей версии. Продавцу банк сообщает, какие не прошли и почему.
6. **Замена:** до срока поставки и до финального void продавец может прислать `version + 1` с заменой непрошедших позиций. Принятые позиции неизменны, **P не убывает**. Повтор уже принятой версии банк отклоняет. Окно претензий B для позиций новой версии идёт от её приёма.
7. **Принять всё равно:** только человек покупателя, до финального void и в пределах суммы блокировки. Человек видит по каждой позиции код, нарушенный предикат и замаскированное значение поля (как уведомление о расхождениях по UCP 600 ст. 16); согласие на расхождения — как waiver по UCP 600 ст. 16(b). Позиции выдаются после оплаты.
8. Данные, переданные покупателю мимо банка, — риск продавца: оплата только за поставку через банк.
9. **Недоступность приёма у банка — ошибка банка:** срок поставки продлевается на время сбоя, сбои публикуются.

### 5.3 Данные
- Для транзитной доставки банк — **обработчик** покупателя (GDPR ст. 28); для хранения доказательств, AML и статистики — **самостоятельный контролёр** [Р].
- Набор хранится до конца окна и решения споров, затем удаляется; непрошедшие позиции — до конца срока замены. В журнале остаются хэши, манифесты, результаты автокодов, снимки источников и позиции, на которые ссылаются претензии.
- Продавец гарантирует законность источника данных и права на их передачу.
- В продуктиве хранение набора — у дочерней компании банка по договору аутсорсинга (руководство EBA по аутсорсингу); автокоды и P считает банк [Р].
- Продавец — физлицо-предприниматель вправе запросить проверку результата автокодов человеком (GDPR ст. 22).

## 6. Автоматические коды (без людей, У1 и У2)

Опора внедрённая: проверка документов на соответствие условиям (UCP 600 ст. 14). Проектная: криптографический класс споров ADRP §6.1 и критерии приёмки мандата корзины ADRP §11.

| Код | Как банк проверяет | Результат |
|---|---|---|
| `NO_DELIVERY` | Нет принятой поставки к сроку | Финальный void, всё покупателю |
| `SHORT` | `count` < заказанного | Оплата за поставленное; не штрафуется, видно в доле выполнения (§9) |
| `BAD_SIGNATURE`, `WRONG_DEAL`, `ROOT_MISMATCH` | Подпись, привязка, пересчёт корня | Поставка не принята; можно прислать заново до срока |
| `SCHEMA_FAIL` | Позиция не проходит JSON-схему из условий | Не оплачивается и не выдаётся |
| `DUPLICATE` | Совпадает `unique_key` внутри поставки | Не оплачивается и не выдаётся |
| `CRITERIA_FAIL` | Позиция не проходит предикаты из условий | Не оплачивается и не выдаётся |
| `REGISTRY_CONTRADICTION` | Позиция противоречит публичному реестру на дату поставки (например, IČO прекращено в ARES, компания в ISIR) — если такой предикат есть в условиях задачи | Не оплачивается и не выдаётся |
| `OUT_OF_MANDATE`, `DOUBLE_PAYMENT` | Журнал мандата и сделок | **Ошибка банка:** возврат из денег банка не позднее конца следующего рабочего дня (PSD2 ст. 73 / zákon 370/2017 Sb.). Продавца не касается |

**Предикаты** — фиксированный словарь: `required`, `eq`, `in`, `range`, `regex` (только RE2), `json_schema` (лимит глубины и времени, без внешних `$ref`), `unique` (внутри поставки), `max_count`, `registry_active` (поле с IČO действует в ARES и не в ISIR на дату приёма). Произвольного кода и ИИ нет. Код проверяет **то, что продавец сам заявил в позиции** и что видно в публичных реестрах, а не качество.

ИИ в денежном пути нет: модель извлекает предикаты, решающее значение имеет подтверждение человека. ИИ-судья из текущего кода убирается.

## 7. Правила качества (то, что кодом не проверяется)

Продавец выбирает правило в предложении в пределах требований мандата. Все суммы — от **P**.

### A «Без претензий по качеству»
Только автокоды. Выплата P и финальный void — в срок поставки (не позднее N рабочих дней) или раньше, если человек покупателя подтвердил приёмку. Перед автоматическим принятием покупатель получает уведомление.

### B «Гарантия качества X %» (X ∈ {5, 10, 20})
- Покупатель возвращает до X % от P **без разбирательства**, указав позиции и причину из списка (`closed`, `wrong_data`, `irrelevant`, `other`).
- Это **заранее объявленное правило возврата продавца**, заложенное в цену, — как Visa Rapid Dispute Resolution, где мерчант заранее задаёт правила автоматических возвратов. Не защита от мошенничества.
- Лимиты покупателя (показываются **до сделки**, §3):
  - не больше 2 претензий B на пару «покупатель–продавец» за 30 дней;
  - новый покупатель (меньше 20 сделок) — не больше 2 претензий B за 30 дней всего;
  - доля сделок с претензией B > 30 % за 30 дней — B недоступна.
  - Если B недоступна — сделка по цене A или отказ. Оплаченная гарантия не отнимается задним числом.
- Претензии B не входят в санкции против продавца (у Visa немошеннические возвраты через RDR не входят в долю споров VAMP; мошеннические с 01.04.2025 учитываются). В открытой статистике видна **частота претензий B по числу независимых покупателей**, без причин (§9). Банк по претензиям B проверяет только признаки мошенничества и сговора.

### C «Спор с внешним решающим» (У2)
1. **Одна претензия C на сделку.** Отзыв = отказ от C по этой сделке. **D — спорная сумма** (сумма к оплате спорных позиций), не сумма сделки.
2. **Доказательство — только датированное до поставки:**
   - снимок источника, сохранённый сервисом банка при приёме (по `source_url`, §5.1);
   - или более ранняя датированная копия в публичном веб-архиве, или журнал изменений самого источника с датой до поставки.
   Снимок, сделанный после поставки, доказательством не считается (данные могли устареть за окно). Бремя доказывания на покупателе; позиция без такого доказательства решается в пользу продавца; недоказуемое — только B. Факты из реестров проверяются автоматически (`REGISTRY_CONTRADICTION`, §6). Опора: chargeback по коду причины требует документов (Visa).
3. **Сначала переговоры** 2 рабочих дня: продавец может согласиться — возврат без сборов. Опора: переговорный этап Escrow.com, бесплатная медиация Upwork, переписка до обращения в администрацию у plati.market.
4. **Сборы обеих сторон вносятся, а не блокируются** (как арбитражный сбор у AAA и Upwork; у Upwork на согласие и оплату — 7 дней): F = база 50 € + 2 € за спорную позицию, не меньше 10 % D, не больше 1000 €. Покупатель — при переходе к решающему; продавец — в течение 7 дней. Обе стороны **платят сразу** (capture на клиринговый адрес банка; авторизация с `maxFeeBps = 0`). Не внёс — решение в пользу внёсшего (у Upwork при ответе одной стороны средства уходят ей).
5. **Сбор не зависит от исхода** (как у AAA и Upwork): решающему банк платит из сбора проигравшего; сбор выигравшего банк возвращает отдельным переводом. При доле (например, 60/40) — пропорционально.
6. **Назначение решающего без возможности подобрать** (порядок «обязательство → раскрытие»):
   - пул — все аккредитованные решающие минус объективные отводы (общий бенефициар со стороной, дела с той же стороной за 90 дней);
   - каждая сторона может отвести до 2 решающих: при открытии стадии решающего стороны записывают в сеть **хэши** своих отводов;
   - претензия заранее фиксирует номер будущего раунда drand R+N;
   - после раунда R+N стороны раскрывают отводы; решающий выбирается по раунду, вышедшему после раскрытия;
   - **личность решающего сторонам не раскрывается до решения**.
7. **Выборка:** если спорных позиций больше k, решающий проверяет случайную выборку k по отдельному раунду drand, вышедшему после назначения, и распространяет результат на долю (как статистическая выборка с экстраполяцией в аудитах переплат Medicare, CMS Program Integrity Manual гл. 8) [Р].
8. Решающий решает за 48 ч. **Опоздал** → удержание и замена решающего (замена арбитра предусмотрена регламентами AAA/ICC [Р]; проектная опора — ADRP §10.2 `hold_and_reassign`); неустойка по договору с банком, повторные опоздания — исключение из пула. Деньги остаются в эскроу (срок длинный, §8.3). По умолчанию никто не выигрывает.
9. **Исполнение решения** — как в UDRP п. 4(k): банк исполняет решение через 10 рабочих дней, если ни одна сторона не подтвердила подачу иска в суд; если подтвердила — деньги остаются в эскроу до решения суда или соглашения сторон.
10. **Лимиты споров:** не больше 2 открытых C одного покупателя против одного продавца; у продавца — не больше `max(3, 5 % его открытых сделок с правилом C)` одновременно на рассмотрении, остальные ждут (деньги — в эскроу).
11. **Правовая природа:** решение решающего — условие **исполнения поручения банку** по договору эскроу (OZ §548), как в UDRP: регистратор исполняет решение панели, суд открыт. Договор купли этим не меняется (§1749–1750 к нему не применяются). Не арбитраж по zákon 216/1994 Sb., не решение банка [Р].

## 8. Выплаты и сроки эскроу

### 8.1 Ограничения AuthCaptureEscrow (проверено по исходнику)
- capture — только оператор и только до `authorizationExpiry`; void — только оператор, в любой момент, **один раз, весь остаток**; reclaim — только плательщик, после срока; refund — оператор, до `refundExpiry`, через коллектор (OperatorRefundCollector — деньгами оператора); capture — не больше `maxAmount`.
- Получатель фиксирован в PaymentInfo. Комиссия — при capture, в пределах `[minFeeBps, maxFeeBps] · amount`, **вычитается из суммы capture**; при `feeReceiver = 0` получателя выбирает оператор — поэтому ставим счёт банка.
- Одну PaymentInfo нельзя авторизовать повторно (`PaymentAlreadyCollected`).
- Авторизация через ERC3009PaymentCollector требует подписи плательщика (`receiveWithAuthorization`, `validBefore = preApprovalExpiry`); для покупателя её делает банк как держатель ключа, для продавца — только сам продавец.
- `paymentState` даёт `capturableAmount` и `refundableAmount` (= захвачено − возвращено), но не «выплачено».
- Если плательщик в чёрном списке EURC или заморожен в tCZK, void и reclaim откатятся — плательщика не замораживать, пока эскроу открыт.
- Итог: все capture по нарастающей, **все возвраты покупателю — одним финальным void**; замена позиций и «принять всё равно» — до финального void.

### 8.2 График

| Момент | A | B | C (У2) |
|---|---|---|---|
| Поставка принята, автокоды | — (ждём срок поставки или подтверждение человеком) | capture `(1 − X) · P` | ничего |
| Срок поставки / подтверждение | capture P, финальный void | — | — |
| Конец окна | — | capture бесспорного остатка, финальный void | capture бесспорного; если спора нет — финальный void |
| Решение спора C (после 10 раб. дней по §7C.9) | — | — | capture доли продавца, финальный void |

Сборы C — отдельные авторизации, сразу capture на клиринговый адрес банка; возврат выигравшему — переводом (§7C.4–5). Возврат за непрошедшие позиции покупатель получает в финале. Это прямо в условиях.

### 8.3 Сроки
- **Срок эскроу длинный, а сделку закрывает банк сам** (capture и финальный void). Поскольку оператор может сделать void в любой момент, длинный срок не ухудшает защиту покупателя, а деньги не проходят через его кошелёк посреди спора.
  - У1: `authorizationExpiry = срок поставки + окно + 30 дней`.
  - У2: `authorizationExpiry = срок поставки + окно + 120 дней` (переговоры, сборы, решающие, очередь, 10 рабочих дней UDRP, AML-отсрочка по §20 с продлениями).
- `refundExpiry = authorizationExpiry + 30 дней` (только для ошибок банка).
- Сроки сделки задаются в рабочих днях по чешскому календарю праздников и при авторизации переводятся в метки времени.

### 8.4 Учёт выплат, сбои и исключения
- **Учёт на уровне сделки:** «выплачено» = Σ `PaymentCaptured.amount` (валовые суммы) **по всем PaymentInfo сделки**, считанные в финализированных блоках. Каждый следующий capture и любая новая авторизация считаются от этой суммы.
- **Rollover — только исключение** (если спор или суд выходит за 120 дней): атомарно, одним вызовом смарт-контракта оператора (void и authorize в одной транзакции) на текущий `capturableAmount`; новая PaymentInfo с солью `keccak(deal_id ‖ n+1)`; продавец получает уведомление и повторяет `verify_escrow`. Без атомарного контракта — новая авторизация только после подтверждения void в финализированном блоке.
- Один ключ оператора в HSM с резервной копией, одна очередь транзакций, второй RPC-узел, резервный узел без ключа. Идемпотентный ключ `deal:hash:capture:n`.
- **Сбой capture:** повторы; срок длинный, поэтому истечение — крайний случай. Если всё же истёк: rollover на (причитается − выплачено по сделке) и capture. Если у покупателя нет средств, банк платит продавцу недостающее из своих средств и получает требование к покупателю. Двойной выплаты нет.
- **Выключатель:** если **инфраструктурные** сбои затрагивают больше N сделок или сумму больше M, банк приостанавливает новые авторизации. Сбои из-за санкций и заморозок не считаются.
- **Санкции против продавца посреди эскроу:** capture не делается; финальный void; обязанность покупателя по оплате приостанавливается; уведомление FAÚ; дальше — по процедуре Reg. 269/2014 [Р].
- **AML-отсрочка** (zákon 253/2008 Sb. §20: 24 ч, продление FAÚ, ещё продление после уголовного заявления): деньги остаются в эскроу, в сети ничего не происходит (срок длинный); после решения — capture или void. Для всех сделок сроки на странице — «до N рабочих дней», поэтому отсрочка не отличается от обычной сделки (§38, запрет разглашения).

## 9. Мониторинг и открытая статистика

Доли сглаженные: `(события + 1) / (наблюдения + 20)` за 30 дней. Пороги абсолютные, по каждому показателю отдельно. **Независимые** и **устойчивые** покупатели — без общих признаков с продавцом и между собой (EvSM, бенефициар, IP, ключи).

**Открытая статистика продавца** (видна агенту покупателя до сделки):

| Показатель | Как считается | Что значит |
|---|---|---|
| Доля выполнения | Поставлено / заказано | Надёжность поставки |
| Брак по позициям | Доля позиций с `CRITERIA_FAIL`, `SCHEMA_FAIL`, `DUPLICATE`, `REGISTRY_CONTRADICTION` | Аккуратность, **не качество**: предикаты публичны, продавец может отфильтровать заранее |
| Доля сделок с правилами B и C | — | Готовность продавца отвечать за качество |
| Частота претензий B | Число независимых покупателей, подавших B, к числу сделок с B; без причин | **Сигнал качества** |
| Проигранные споры C | К числу сделок с правилом C | **Сигнал качества** |
| Устойчивые покупатели | Число покупателей старше 90 дней со сделками у ≥ 3 разных продавцов на сумму ≥ порога | Защита от накрутки |

| Кто | Что | Порог | Последствие |
|---|---|---|---|
| Продавец | Брак по позициям | > 5 % | Только правила B/C |
| Продавец | Проигранные C | > 10 % сделок с C | Только У2 |
| Продавец | Доля выполнения | < 80 % | Предупреждение в статистике |
| Продавец | Претензии B от ≥ 3 независимых покупателей | Внутренний порог | Проверка на мошенничество и сговор, не на качество |
| Покупатель | Претензии B | §7B | B недоступна (видно до сделки) |
| Покупатель | Проигранные C | ≥ 3 за 30 дней | Сбор F ×2 в пределах бюджета мандата |
| Пары | Встречные сделки, общий бенефициар, цена вне истории | Правила AML | В комплаенс, без уведомления клиента |

## 10. Экономика

| Статья | Кто платит | Сколько (предложение) |
|---|---|---|
| Комиссия за сделку | Продавец, при capture (`feeReceiver` = счёт банка) | У0 0,2 % (раз в месяц), сессия 0,2 %, У1 0,8–1,2 %, У2 1,5 % |
| Сбор за спор C | Проигравший — решающему, через банк | 50 € + 2 € за позицию, ≥ 10 % D, ≤ 1000 € |
| Неустойка за просрочку решающего | Решающий по договору с банком | По договору |
| Ошибки банка | Банк | По факту, D+1 |
| Сбой инфраструктуры | Банк | Недостающее по сделке, с требованием к покупателю |
| Газ | Банк (tCZK — релейер) | Base: доли цента, проверить |

- **Банк** зарабатывает комиссию только при capture; окупается объёмом; KYB и реестры уже есть. Честно: рынок B2B-данных для агентов ещё мал [Р].
- **Решающий** получает сбор всегда; сбор растёт с числом позиций, проверка идёт по выборке. Ориентир: у Upwork арбитражный сбор — сотни долларов на сторону.
- **Продавец**: доступ к покупателям, чей мандат требует защиты; деньги заблокированы до поставки; при A — выплата в срок поставки. Сравнение: карточный чарджбэк и Escrow.com.
- **Покупатель**: защита от непоставки, недопоставки, несоответствия заявленному и реестрам, обмана агента и платежа не тому — без людей; от плохих данных с датированным доказательством — C; от остального — B и статистика.

## 11. Путь, который человек может отследить

- Каждое событие (поставка, автокоды, претензия, переговоры, сборы, отводы, назначение решающего, решение, срок на иск, capture/void) — запись в журнале с хэш-цепочкой.
- Страница сделки: условия человеческим языком (и кто их подтвердил), что пришло, какие позиции не прошли и почему, куда пошли деньги, ссылки на транзакции, что будет при молчании и до когда («до N рабочих дней»).
- Для клиента — нейтральные тексты при AML, полные — только для комплаенса.

## 13. Новизна (честно)

Не наше:
- **Внедрённое:** выдача против оплаты (инкассо, URC 522), проверка документов на соответствие, частичные выплаты и согласие на расхождения (аккредитив, UCP 600), сверка данных с обязательством банка (BPO, ICC URBPO); окно проверки и переговоры до арбитража (Escrow.com); автовыплата при молчании, сборы с обеих сторон, внешний арбитраж (Upwork, AAA); исполнение решения панели с окном на иск (UDRP); правила автоматических возвратов мерчанта и документы по коду причины (Visa).
- **Проектное:** мандаты намерения и корзины, подписанные человеком (Google AP2); критерии приёмки мандата корзины, детерминированные проверки, уровни, сборы, удержание и переназначение (ADRP, черновик); эскроу Commerce Payments (Coinbase); подключаемый арбитр (x402r); lockup и долг получателя (Circle Refund Protocol, без аудита); частичные возвраты и контроль риска по продавцу (Agentic Settlement Protocol, arXiv 2609.02208); эскроу по использованию (Fortytwo); случайный выбор (Kleros, drand).

Наше — у аналогов не нашли:
1. **Исполняет регулируемый банк, который держит счёт плательщика:** мандат, проверки, выдача и оплата — в одном регулируемом контуре; у агента нет денежных ключей.
2. **Поштучно и автоматически в момент поставки:** банк сам пересчитывает каждую позицию по условиям, подтверждённым человеком, и по публичным реестрам, выдаёт только принятые и платит за них — без людей.
3. **KYB по реестрам ЧР** (ARES, ISIR, реестр НДС, EvSM) до платежа и в предикатах.
4. **tCZK**, согласованный с эскроу: новое для ЧР, не для мира.

## 14. Демо (3 минуты: 3 живых эпизода)

1. **Лимит и атака** (40 с): агент пытается превысить мандат → отказ / подтверждение человеком; продавец в переговорах просит «платите на другой адрес» → деньги не двигаются.
2. **Автокоды** (40 с): продавец прислал 20, 3 не прошли условия (одна — закрытая по ARES фирма) → 17 выдано и оплачено, 3 не выданы и возвращены одним void, без людей; ссылки на транзакции.
3. **Путь спора C** (60 с, ускоренное время, транзакции прогнаны заранее, показ по ссылкам): претензия по 10 позициям со снимками источников при приёме → переговоры не удались → оба сбора уплачены → решающий назначен жребием drand → выборка 5 позиций → решающий (человек на сцене) признал 3 из 5 → 60 % спорной суммы возвращено, 40 % выплачено продавцу; capture/void доли и сборов на странице сделки.

B, сессии, rollover, статистика, tCZK и НДС — устно в ответах на вопросы.

**Минимум кода для демо:** движок предикатов (включая `registry_active`), выдача только принятых позиций, один финальный void, сборы на клиринговый адрес, жребий drand, страница сделки; ИИ-судья отключён.
